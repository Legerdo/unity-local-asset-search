# 검색 품질: 메타데이터 효과와 내용 검증

제품 모델은 EmbeddingGemma 2로 유지합니다. 이미지 내용 검색은 아래의 작은 표본에서 확인했지만 효과음 검색 정확도를 확정할 독립 청취 정답은 아직 없습니다. 이 문서는 같은 날 수행한 후속 검증까지 반영합니다. 파일명 기반 참조 포함 결과를 소리 이해 성능으로 해석하지 않습니다.

## 파일명을 가린 새 표본

앞선 검증과 내용 해시가 겹치지 않는 이미지·오디오·문서 각 16개, 총 48개를 사용했습니다. 이미지 이름을 가린 미리보기를 보고 검색 전에 내용 질의 9개와 관련 ID를 고정했습니다. 음향특성 질의 5개는 파형의 길이·주파수 분포·peak/RMS로 정했습니다. 후자는 총성·발소리 같은 사건의 청취 정답이 아닙니다.

| 입력 조건 | 이미지: 관련 자료 1위 / 상위 5개 포함 (9질의) | 음향특성: 1위 / 상위 5개 포함 (5질의) |
|---|---:|---:|
| 메타데이터 제외 | 9 / 9 | 1 / 5 |
| 메타데이터 포함 | 9 / 9 | 0 / 4 |
| 다른 파일의 메타데이터로 교체 | 8 / 9 | 1 / 4 |
| 메타데이터만 | 6 / 7 | 0 / 2 |

이미지의 성과가 파일명에만 의존했다는 해석은 이 표본과 맞지 않습니다. 오디오는 메타데이터를 추가해도 파형 특성 검색이 개선되지 않았습니다. 아래의 파일명 참조 검사에서 얻은 오디오 12/12는 내용 이해의 증거가 아닙니다. 이 실험의 메타데이터 제거/교체 옵션은 제품 UI에 노출하지 않았습니다.

## 오디오 독립 모델과 대조

기존 로컬 생성 모델을 판정기로 쓰려 했지만 무음·순음·백색소음 대조에서 잘못된 설명을 내놓아 정답 생성에 사용하지 않았습니다. 이후 가벼운 EfficientAT `mn05_as` 분류기를 CPU로 실행했습니다. 세 대조에서 Silence/Sine wave/Static 또는 White noise를 구분했습니다. 같은 실제 음원 16개 중 9개에만 사전 기준을 통과한 태그를 부여했고 불확실한 7개도 검색 후보에 남겼습니다.

이 태그에서 고정한 8개 질의와 미리 작성한 바꿔 쓴 표현 8개를 CLAP Q8과 EmbeddingGemma 2에 동일하게 적용했습니다. 파일명·폴더를 제외하고 실제 파형과 문장을 각 모델의 공유 공간에 임베딩했습니다.

| 항목 | CLAP HTSAT Q8 | EmbeddingGemma 2 |
|---|---:|---:|
| 자동 참조가 1위 | 5/16 | 3/16 |
| 상위 5개에 자동 참조 포함 | 11/16 | 10/16 |
| 자동 참조 MRR | 0.463 | 0.382 |
| 문장 인코딩 평균 | 3.35ms | 61.41ms |
| 16음원 읽기·전처리·인코딩 | 2.00초 | 2.92초 |
| 무음·순음·백색소음 대조 | 3/3 | 2/3 |

Ryzen 7 9800X3D, 실행기당 4스레드, CLAP INT8 ONNX Runtime 1.31.1과 Gemma Torch CPU FP32의 비교입니다. 모델 시작은 제외하고 대조군으로 워밍업한 뒤 측정했습니다. 질의 벡터 캐시는 재사용하지 않았으며 Unity HTTP/UI 지연이 아닙니다. 두 실행의 참조 순위는 같았고, 음원 시간은 양쪽 모두 읽기·리샘플링을 포함한 두 번째 실행을 사용했습니다.

CLAP가 자동 참조에 더 잘 맞고 CPU 비용도 낮았지만, 정밀도가 다르므로 아키텍처만의 차이로 볼 수 없습니다. EfficientAT와 CLAP가 AudioSet 도메인·어휘를 공유하는 편향도 있습니다. 8개 개념의 두 표현을 16개 독립 개념으로 해석하거나 사람의 청취 정답률로 표현하지 않습니다. CLAP는 비교만 수행했고 제품에는 추가하지 않았습니다.

참고 모델: [EfficientAT](https://github.com/fschmid56/EfficientAT), [Xenova/clap-htsat-unfused](https://huggingface.co/Xenova/clap-htsat-unfused), CLAP 리비전 `c28f2883575e590e04d3146ff0713c2448d691ba`. 임시 다운로드·실행기는 검사 후 삭제했습니다.

## 공개 결과와 재현 범위

실제 리소스는 원본을 복제하거나 수정하지 않고 읽었으며 검사 후 SHA-256이 같음을 확인했습니다. 제3자 원본 에셋·개인 경로·전체 벡터는 배포하지 않습니다. [공개 집계](benchmarks/real-resource-summary.json)에 표본 수·측정값·한계와 로컬 원시 결과의 SHA-256을 기록했습니다. 원시 결과는 로컬 보관이므로 공개 자료만으로 동일 코퍼스를 완전히 재현할 수 없습니다. 공개된 직접 제작 샘플의 재현 절차는 [BENCHMARKS](BENCHMARKS.md)에 있습니다.

## 최초 전처리·검색 구현 점검

2026-10-28. 실제 프로젝트 자료 192개(문서·이미지·오디오 각각 64개)로 진단·전후 비교·제품 코드 재검증을 수행했습니다. 이번 표본은 426벡터이며 앞선 539벡터 표본과 다릅니다. 이번 진단 매니페스트를 고정하고 전후/최종 실행의 192개 SHA-256 목록이 동일함을 확인했습니다. 과거 수치와 직접 A/B 비교하지 않았습니다.

## 원인 판정

- [공식 모델 카드](https://huggingface.co/google/embeddinggemma-2#best-practices)의 16kHz 모노 입력, BF16, 검색어 프롬프트를 확인했습니다. 현재 설정과 일치합니다.
- 오디오 64개의 첫 청크를 단독/배치로 비교한 최소 코사인은 0.999102였습니다. 8개의 짧은 오디오를 파일 경로로 직접 입력한 경우와 현재 배열 전처리의 코사인은 모두 약 1.0이었습니다. 이번 표본에서 전처리 경로 오류나 큰 배치 왜곡은 검출하지 못했습니다.
- 18개 동일 질의의 API 상위 5개 순위가 DB 벡터를 독립적으로 내적해 계산한 순위와 전부 일치했습니다. 정렬·중복 청크 집계 오류도 검출하지 못했습니다.
- 기존 설계는 텍스트에만 제목을 제공하고 이미지·오디오에는 파형/픽셀만 넣었습니다. 짧은 타격음·진동 표본·기술 텍스처는 콘텐츠만으로 개발자의 에셋 의도를 설명하기 어렵습니다. 이 검사에서는 모델 가중치 자체의 결함으로 확정하지 않았습니다. 이후 CPU FP32 오디오 대조를 추가했지만 독립 청취 정답셋 평가는 아직 수행하지 않았습니다.

## 변경

이미지·오디오의 실제 콘텐츠와 읽기 쉬운 파일명 및 가까운 두 폴더 이름을 단일 복합 입력으로 임베딩합니다. 제목 160자·폴더 240자로 제한하고 절대 경로는 넣지 않습니다. 원본 파형/픽셀 전처리, 768차원, 코사인 점수, 필터와 정렬 API는 유지합니다. 점수 가산이나 특정 파일 우대 규칙은 없습니다.

공식 모델이 지원하는 복합 입력을 사용했습니다. 변경된 것은 모델의 순수 소리 인식 능력이 아니라 **메타데이터를 함께 사용하는 에셋 검색**입니다. 부정확한 이름·폴더는 결과를 왜곡할 수 있습니다. 이름이 무의미하거나 소리 자체의 의미만 찾아야 하는 경우에는 한계가 남습니다.

전처리 지문을 v3-media-context-v1로 갱신했습니다. **이전 생성 인덱스는 설정 탭에서 초기화 후 재색인이 필요합니다.** 기존 인덱스를 자동 삭제하거나 이전 벡터와 혼합하지 않습니다.

## 같은 자료·같은 질의의 통합 검색 비교

질의 30개: 원래 표현 18개와 개선 결과를 보기 전에 준비한 바꿔 쓴 표현 12개. 아래는 사전 지정한 파일이 상위 5개에 포함된 건수입니다. 참조 파일이 없는 질의 1개는 표의 분모에서 제외하되 원시 결과에는 보존했습니다.

| 종류 | 질의 묶음 | 변경 전 | 최종 제품 코드 |
|---|---|---:|---:|
| audio | 원래 표현 | 1/6 | 6/6 |
| audio | 추가 표현 | 1/6 | 6/6 |
| image | 원래 표현 | 2/6 | 6/6 |
| image | 추가 표현 | 1/4 | 3/4 |
| text | 원래 표현 | 4/5 | 4/5 |
| text | 추가 표현 | 2/2 | 2/2 |

참조는 파일명에서 정한 약한 라벨입니다. 다른 자료도 정답일 수 있고, 모든 오디오를 청취해 정답을 확정하지 않았습니다. 따라서 표는 회귀/참조 포함 검사이며 정식 Recall@5나 실제 정답률이 아닙니다. 최상위가 항상 맞는 것도 아닙니다. 얼굴 색상 텍스처 질의에 얼굴 노멀맵이 먼저 나온 예처럼 세부 구분의 한계가 남았습니다.

## 최종 제품 코드 검증

- 실제 192개 색인 성공, 실패 0개, 426개 벡터 생성. 변경 없는 재색인은 192개 모두 건너뜁니다.
- 색인 14.56초. 전체 종류의 새 검색어 HTTP 응답 중앙값 46.33ms, P95 58.85ms. UI 표시 시간은 제외됩니다. 별도 성능 질의에는 Find assets matching: 접두어가 있으며, 위 품질 비교는 같은 원문 질의를 사용했습니다.
- 원본 192개 SHA-256 재검사 통과. 각 실행의 임시 인덱스·상태 폴더 삭제 확인. 실제 리소스나 모델을 패키지/Git에 추가하지 않았습니다.
- 회귀 검사: 변경 전에는 미디어 제목 부재로 실패했고, 변경 후에는 제목/상대 폴더가 포함되면서 파형 샘플과 픽셀이 보존되는지 검사해 통과했습니다.
- Backend 19개 + Agent 2개, 총 21개 자동 검사와 101개 로케일 키/UXML 패키지 검사 통과. C#·UI 코드는 변경하지 않았고 이번에 Unity UI 재검증은 수행하지 않았습니다.

실행 게이트: `python -m unittest discover -s Backend~ -p test_*.py -v`, `python -m unittest discover -s Agent~ -p test_*.py -v`, `python Backend~/validate_package.py`, `git diff --check`. 실제 모델 검증은 별도 테스트 스크립트에서 제품 HTTP 핸들러/Engine을 호출했습니다. 전체 재현 스크립트는 로컬 보관 결과에 포함하며 공개 집계에는 원본 에셋 경로를 싣지 않습니다.
